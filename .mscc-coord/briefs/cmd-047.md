## 2. NEW: local Launch and Auto (design approved by Stew; Auto also for remote hosts)

### 2.1 Behaviour

- **Launch is enabled only when Host is `127.0.0.1`, `localhost` or `::1`** (same test as `IsRemoteAudioAllowed`, MainViewModel.cs:339-351, and :2358-2359; make one `IsLocalHost(string)` helper and use it in all three places). Also disabled while connected or busy. For any other Host the Launch box is grey and ignored (servers on another computer are never started or stopped from here).
- **Auto works for any Host** (local or remote): it only presses Connect when MSCC UI opens. Enabled whenever not busy (it is a start-up preference, so it can be changed while connected). With a remote Host, Auto just connects; Launch stays out of it.
- Persist in `~/.config/MSCC/mscc-avalonia.ini` (ClientSettingsStore.cs): `LAUNCH_SERVERS` (default **1** when the key is missing) and `AUTO_START_SERVERS` (default **0**). Follow the existing pattern (write at :239-316 area, read in the `switch` at :435+).
- **Launch checked + Connect** (localhost only, Linux only; on Windows log `Launch: Linux only` and just connect):
  1. If `ms-sdr`, `sdrcore-recv` and `sdrcore-trans` are **all** running: log ` Launch: servers already running - connect only (not ours)`, `_serversOurs = false`, connect.
  2. Otherwise:
     - Pre-flight warning (a **warning, not a lockout**): if `~/mscc/ms-sdr` is missing/not executable, or `~/.local/mscc/` is missing, or `~/.local/mscc/comm-port.ini` (read by ms-sdr `comm-port.c`) or `~/.local/mscc/operator-speaker.ini` (read by sdrcore-recv) is missing, show `MSCC is not set up on this computer yet. Run MSCC Init (menu: MSCC Init), then try again.` via `MsccDialog.AlertAsync`, log it, then carry on with the start anyway.
     - Run the start command (resolve in this order, first that exists wins):
       1. `/usr/local/bin/mscc-desktop-ctl start` (it runs `mscc-virtual-audio` itself and shows a desktop notification);
       2. else `mscc-virtual-audio` (`/usr/local/bin/mscc-virtual-audio`, ignore failure), then `mscc start` with `mscc` = `/usr/local/bin/mscc`, fallback `~/mscc/mscc.sh`;
       3. none found: status `mscc not installed - start the servers with MSCC Start`, log, and still try to connect.
     - Log every output line with a ` [mscc] ` prefix. Timeout 30 s.
     - If any of the three was not running before, set `_serversOurs = true` (also for a partial start: `mscc start` skips the ones already running, and `mscc stop` will stop all three; log ` Launch: partial (N of 3 running) - mscc start fills in, marked ours`).
     - Wait until all three processes are up (poll every 250 ms, max 10 s), then **3 s settle** (ms-sdr opens USB), then `new UdpRadioService(...)` and `StartAsync(launchSubsystems: false)` exactly as today. Status texts: `Starting servers...`, `Waiting for servers...`, then the normal `Connected ...`.
     - After Connect, the first 0xF4 keep-alive (already counted in `PacketReceived`, :6436-6441) logs ` Launch: server alive (first keep-alive)`.
- **Disconnect** (`Disconnect` :1254-1311) and **window close**: after `DisposeRadio()`, if `_serversOurs`: run `mscc stop` (same resolution; `mscc-desktop-ctl stop` is fine too), log the output, `_serversOurs = false`. If not ours: log ` Launch: servers not started by this client - left running`. Change the Disconnect log line (:1260) to say which case applies.
- **Auto checked**: when the window opens (`MainWindow.OnOpened`, MainWindow.axaml.cs:24-27), if Auto is checked (**any Host**), post a Connect about 0.5 s later (`if (vm.ConnectCommand.CanExecute(null)) await vm.ConnectCommand.ExecuteAsync(null);`). Log ` Auto: Connect on start (Host X)`. With a local Host and Launch checked, that starts the servers too; with a remote Host it is a plain Connect. If that Connect fails, show the normal error; don't retry.
- Works the same on the Pi (same process names; `rpi/mscc-deb` ships `mscc-desktop-ctl` and `mscc.sh` with the same start list). Read those only, never edit `rpi/`.

### 2.3 Environment for the child process (important)

The package launcher `/usr/bin/mscc-ui` (packaging/mscc-ui/usr/bin/mscc-ui) and `~/mscc-ui/mscc-ui` put the app folder (`/opt/mscc-ui` or `~/mscc-ui`) **first** in `LD_LIBRARY_PATH`. The servers must not inherit that (the app folder is full of .NET / Skia natives). In `ProcessStartInfo.Environment`, remove every `LD_LIBRARY_PATH` entry equal to `AppContext.BaseDirectory` (trimmed of the trailing `/`), `/opt/mscc-ui` or `~/mscc-ui`; drop the variable if nothing is left. `mscc.sh` adds `/usr/local/lib` itself. Also `RedirectStandardInput = true` and close it at once, `UseShellExecute = false`.

### 2.4 Close while the servers are ours

A child whose stdout is a pipe to MSCC UI can die with SIGPIPE when MSCC UI exits. So on **window close** do not use pipes: start `/bin/sh -c '<mscc> stop >> "$HOME/.local/share/MSCC-Avalonia/logs/mscc-launch.log" 2>&1'` detached (no redirects in `ProcessStartInfo`), log one line ` Launch: close - mscc stop started (log: ...)`, and let the window close. (The app log folder is `LocalApplicationData/MSCC-Avalonia/logs`, VM :141-146.) On **Disconnect** (app stays open) the piped `RunAsync` with logging is fine; run it off the UI thread and keep `_serverStopTask`.

### 2.5 Close / Disconnect order (with section 4)

1. If a FREQ CAL AUTO/CHECK is running: `AbortCalibrationAsync()` (bounded wait about 200 ms).
2. If the FREQ CAL tab holds CW: restore mode / CW filter / pitch and await the sends (bounded about 300 ms total).
3. Existing Disconnect work (remote off, `ForceTxOffAsync`, force-stop other cals, `DisposeRadio`).
4. `mscc stop` only if `_serversOurs`.
5. For Close only: then `SaveLastUsedForCurrentBand` / `SaveClientSettingsNow` (already in `Dispose`, :7091-7093), so the ini gets the user's filter / pitch, not 200 / 600.

Avalonia's `Closed` event (MainWindow.axaml.cs:20, :316-333) is too late for async work. Add a `Closing` handler: first time, `e.Cancel = true`, `await vm.PrepareForCloseAsync()` (steps 1-4, overall cap about 1.5 s plus the detached stop), set `_closeReady = true`, then `Close()` again. Keep `Dispose()` as the backstop (add `if (_freqCalEntryHeld) LeaveFreqCalTab(sendToRadio: false)` at its top so the saved ini is right even if Closing was skipped).

### 2.6 Cold-start keep-alive grace

Core only gives the 20 s cold-start grace when it launched the backends itself (UdpRadioService.cs:303-310), which we never do. We wait for the processes + 3 s before connecting, so this is usually fine. As a safety net, in the `ServerKeepAliveLost` handler (VM :6850-6855): if `_serversOurs`, less than 45 s since `_serversLaunchedUtc`, no keep-alive received yet (`_keepAlivesReceived == 0`) and the grace was not used yet, call `_radio.ResetKeepAliveWatch()` once, log ` Launch: cold start - keep-alive grace extended`, and don't show the WARNING. Otherwise keep today's behaviour. (Core logs "user chose Continue" on reset; that's cosmetic, leave Core alone.)

## 8a. cmd-041: DIG-U Hi 1.4k and 1.0k (match WPF)

How WPF does it (cmd-041 `3f52fc1`, read on stew-HP with `git show 3f52fc1`; WPF MainViewModel.cs `HighCutButtonOptions` / `HighCutCount` / `NormalizeHighCut` at stew-HP HEAD :511-531): the Hi button has **7** entries, indexes 5 = 1.4 kHz and 6 = 1.0 kHz are **DIG-U only**; other modes stay on 0-4 and an index above 4 clamps to 4 (2.4k). The client sends **Hz** through Core `SetFilterHighAsync(hz)`; Core `HighCutHzToIndex` turns 1400 / 1000 into 0xD1 (`CMD_SET_BW_HICUT`) index 5 / 6; ms-sdr passes it through; recv maps 5 -> 1400, 6 -> 1000 (Linux `linux/SDRcore-recv-linux/sources/udp_thread.c` `case CMD_SET_BW_HICUT`, in 1.0.47). The RX/TX-tab default HIGH list (0xDD) stays **5** items, and WPF ignores a 0xDD report above 4 (ms-sdr echoes the last live 0xD1 as the default on connect).

Avalonia differences to respect: one shared `_highCutIndex` for every mode (no per-mode profile), Hi cycles **up** (5.5k -> 4.0k -> ... -> 2.4k), labels are short (`2.4k`). Keep both. So:

- Tables (MainViewModel.cs:29-30): `HighCutLabels = { "5.5k", "4.0k", "3.0k", "2.7k", "2.4k", "1.4k", "1.0k" }`, `HighCutHzValues = { 5500, 4000, 3000, 2700, 2400, 1400, 1000 }`. **Leave `HighCutOptions` (:489-490, the default HIGH list) at 5 items.**

## Known risks

- **Tab revert loop:** re-selecting FREQ CAL inside `SelectionChanged` can re-enter the handler. Use a guard flag and `Dispatcher.UIThread.Post`.
- **Close timing:** Avalonia `Closed` is too late for async sends. Without the `Closing` cancel-and-retry (2.5), CW/200/600 gets saved to the ini and left on the server.
- **Server version:** STOP/drain needs ms-sdr with `CMD_SET_CAL_ABORT` and Hi 1.4k/1.0k needs recv with `CMD_SET_BW_HICUT` 5/6 (Ubuntu 1.0.47 via cmd-043, **installed on stew-HP now**; Pi 1.0.46; Windows 3.176 / recv 3.141). Against an older server STOP only falls back to the 36 s client timer, and an old recv ignores Hi 5/6 (keeps the previous width). Not an issue for this local run.
- **Hi 1.4k/1.0k with one shared Hi:** Avalonia has no per-mode filter memory, so leaving DIG-U at 1.0k drops Hi to 2.4k and going back to DIG-U does not bring 1.0k back (WPF does). Accepted for now; tell Stew. Watch that a radio `USB` report that keeps the DIG-U overlay does **not** clamp (8a).
- **0xDD echo:** ms-sdr stores the last live 0xD1 (5 or 6) and reports it as the default on connect; without the 8a guard the 5-item default HIGH list would show 2.4k.
- **DKMS:** needs headers for each new kernel (the `linux-headers-generic` metapackage is installed, so they come with kernel updates). If a future kernel breaks the tty0tty build, CAT stops until fixed; the old kernel still boots from GRUB.
- **"Ours" is session memory:** if MSCC UI crashes, servers it started keep running (next Connect sees them running, calls them "not ours" and won't stop them; `mscc stop` by hand). Accepted.
- **Two clients on one host:** a second MSCC UI with Launch sees the servers running and won't stop them; the first one will stop them on Disconnect. Accepted (same as WPF Launch Servers).
- **Partial start:** if only some servers were running, `mscc stop` on Disconnect stops all three.
- **LD_LIBRARY_PATH** inheritance (2.3) and **SIGPIPE on close** (2.4).
- **VFO A forced active at startup** changes today's Avalonia behaviour (it restored `USE_VFO_A`). This is the WPF rule; tell Stew.
- FREQ CAL with VFO B active: the tab now snapshots and restores the active VFO; test once on B if time allows.
