## Implement (hypothesis — labeled)

**Change stays in WPF mic sender only.** Match the clean Pi-as-client pattern:

1. **Dedicated capture thread** (e.g. background, AboveNormal) that owns pacing and send.
2. Read a **fixed 10 ms** block = **480 mono frames** @ 48 kHz (keep existing `FramesPerPacket`).
3. **Block until those samples exist**, then send **exactly one** MSA1 UDP packet, then read the next block.
4. Packet rate must follow the **sound-card / capture clock**, not WaveIn callback jitter.
5. Keep MSA1 framing unchanged (48 kHz mono s16, existing header write). Prefer WPF-only — do not port Avalonia/PortAudio unless needed; NAudio WaveIn/Wasapi with a producer queue + blocking consumer thread is fine if it meets the contract (callback must **not** call `_udp.Send`).

### Suggested shape (non-binding)

- Callback (if WaveIn kept): only enqueue PCM into a thread-safe buffer/queue; never send UDP there.
- Capture thread: wait until ≥480 mono samples ready → fill packet → `WriteHeader` → `Send` → repeat while running.
- Stop: stop capture, join thread with timeout, dispose UDP as today.
- Preserve: device list UI, volume, stereo→mono max-abs channel pick, host resolve, logging cadence.
