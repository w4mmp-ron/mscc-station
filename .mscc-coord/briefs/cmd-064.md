## Why

1. **The spur was never just DC.** A raw I/Q recording on the Pi (dummy load) shows, around
   DC: the DC offset, a comb at 16.08 Hz and its harmonics, and noise that rises toward DC
   and is still above the floor about 300 Hz out. `doPanadapter` runs on the raw I/Q before
   the 12 kHz shift, so all of it shows at VFO -12 kHz. That is why the notch needed
   +/-6 FFT bins. A 1.5 Hz DC blocker (0.9999) was tried first: the spur stayed.
2. **The spectrum FFT was half empty.** An audio block is `nfft - filtertaps` = 2048 frames,
   but `doPanadapter` copies `nfft` = 4096 samples from `incplx`. The upper 2048 are never
   written (zeros). So the 4096 Hamming window is cut off at its peak: a strong signal leaks
   about -21 dB at 6 bins away (a proper window: -43 dB or better). Wide skirts on every
   strong signal, and the real resolution was ~47 Hz, not 23 Hz.

Both are display only. Audio, S-meter, FREQ CAL and image check use `fastconv`, which
already keeps the previous block; the removed slice is 12 kHz outside the audio passband.

## The change

### A. DC blocker on the raw I/Q (`dsputils.c`, `framesToComplex`)

```c
#define DC_BLOCK_A 0.98f   /* 96 kHz: -3 dB at ~300 Hz */
...
        static sp_float dc_xi = 0.0f, dc_yi = 0.0f; // DC blocker state, I
        static sp_float dc_xq = 0.0f, dc_yq = 0.0f; // DC blocker state, Q
        sp_float x;
...
                /* right after the iMult / qMult lines, before the 1.0e-18f lines */
                x = incomplex[i].real;
                dc_yi = x - dc_xi + DC_BLOCK_A * dc_yi;
                dc_xi = x;
                incomplex[i].real = dc_yi;

                x = incomplex[i].imag;
                dc_yq = x - dc_xq + DC_BLOCK_A * dc_yq;
                dc_xq = x;
                incomplex[i].imag = dc_yq;
```

Keep 0.98. 0.9999 and 0.99 are not enough (Pi recording: hump +27 dB with no blocker,
+23 dB at 0.9999, +5 dB at 0.99, about 0 at 0.98).

### B. Full 4096-sample FFT (`dsputils.c`, `doPanadapter`)

Add a history of the last `nfft` samples. Update it on **every** call, before the
`panReady` / `G_tx_mode` early return, so the two halves always join without a gap:

```c
        static sp_cplx pan_hist[4096];
        int keep;

        if (nframes > mystate.nfft) { // more than one FFT of data: use the newest nfft
                fftbuf += nframes - mystate.nfft;
                nframes = mystate.nfft;
        }
        keep = mystate.nfft - nframes;
        for (j = 0; j < keep; j++) {
                pan_hist[j].real = pan_hist[j + nframes].real;
                pan_hist[j].imag = pan_hist[j + nframes].imag;
        }
        for (j = 0; j < nframes; j++) {
                pan_hist[keep + j].real = fftbuf[j].real;
                pan_hist[keep + j].imag = fftbuf[j].imag;
        }

        if (panbuffer.panReady == 1 || G_tx_mode) {
```

and the copy into the FFT buffer reads `pan_hist[j]` instead of `fftbuf[j]`.

## Level shift (expected, not yet measured)

Change B doubles the number of real samples in the FFT. Calculated:

| | FFT magnitude | on the client dB scale |
|---|---|---|
| Steady signal (carrier) | x2 | about **+3.0** |
| Noise floor | x1.41 | about **+1.5** |

The client scale is `Y / 150 - 40` = `10 * log10(magnitude)` (`RawYToDb` in
`UdpRadioService.cs`, bias 40), so a x2 magnitude reads +3, not +6. Changes A and C do not
move levels.

So after this change the spectrum sits about 1.5 higher on noise and 3 higher on signals,
and the client spectrum dB CAL (`SPECTRUM_DB_OFFSET`) will need redoing once, by about -3 if
it was set on a carrier. Ron has not measured the shift on the Pi yet; **please measure it**
(same carrier and same noise floor, before and after) and report the numbers.
