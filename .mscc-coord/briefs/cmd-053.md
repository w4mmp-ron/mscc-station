# Build brief - cmd-053: spectrum -12 kHz spur notch sized in FFT bins (port from the Pi)

**For:** Stew (N8VET)
**Host:** windows-new-hp (Windows `SDRcore-recv`), then ubuntu-stew (`linux/`)
**Commit on each host when done. Do not push** (Stew pushes).
**Out of scope:** `rpi/` (done, the reference), WPF / Avalonia, ms-sdr, trans, firmware.
**No protocol change.** recv only, `panadapter.c`.

**Reference (Pi, tested on the Pi by Ron 2026-09-29):** commit `b08af65`.
`git show b08af65 -- rpi/SDRcore-recv-linux/sources/panadapter.c`

---

## Why

The -12 kHz spur (IQ DC, at pixel `pixels/3`) is blanked by a fixed 3-pixel patch
(`mp_bin - 1 .. mp_bin + 2`). That fits PAN RESOLUTION 800, but the spur is a fixed number
of **FFT bins** wide, so in pixels it grows with resolution. At 1600 and 3200 the spur
shows next to the patch (spectrum bump + a line in the waterfall).

The display spans FFT bins 1024..4095 (3072 bins, `doPanadapter` in `dsputils.c`, same on
Windows), so 1 FFT bin = `pixels / 3072` pixels.

## The change

- New `#define MP_HALF_BINS 6.0f` (spur half-width in FFT bins).
- `int mp_bin` -> `int mp_lo`, `mp_hi` (first / last pixel replaced):
  ```c
  float c = (float)pixels / 3.0f;
  float w = MP_HALF_BINS * (float)pixels / 3072.0f;
  mp_lo = (int)(c - w + 0.5f);
  mp_hi = (int)(c + w + 0.5f);
  if (mp_lo < 1) mp_lo = 1;
  if (mp_hi > pixels - 2) mp_hi = pixels - 2;
  ```
- Bridge: the segment test is `mp_hi >= Y_source_index && mp_lo < Y_source_index + MAX_X`,
  neighbours `lo = mp_lo - 1 - Y_source_index`, `hi = mp_hi + 1 - Y_source_index` (clamped
  to 0 .. MAX_X-1), fill `lo+1 .. hi-1` with the average of `lo` and `hi` when `hi > lo + 1`.
  A notch across a segment edge is handled per segment.

Width: 800 about +/-1.5 px, 1600 about +/-3 px, 3200 about +/-6 px (about 280 Hz total).
Ron tried 3 and 4 bins first: a small bump was still visible at 3200. 6 is OK ("a bit
blotchy but OK").

## 1. Windows (`mscc-ui/windows-work-tree/SDRcore-recv/sources/panadapter.c`)

The notch code is the same as the old Pi code, but the file differs elsewhere (smoothing
loop; see Note). Port the three hunks of `b08af65` by hand; do not copy the Pi file.
Bump `VERSION_MINOR` in `extern.h` (141 -> 142). Build, copy to `C:\mscc-net9\`.

## 2. Ubuntu (`linux/SDRcore-recv-linux/sources/panadapter.c`)

Identical to the Pi file before `b08af65` (checked 2026-09-29), so copy the Pi file as-is.
Bump `VERSION_MINOR` in `extern.h`. `make clean && make`. No .deb needed just for this; it
rides with the next Ubuntu kit.

## 3. Test (each host)

PAN RESOLUTION 800, 1600, 3200, dummy load or quiet band:
1. No spur at -12 kHz (VFO - 12 kHz) in the spectrum or the waterfall at any resolution.
2. A real signal a few hundred Hz away from -12 kHz still shows.
3. Change resolution while running: no crash, notch follows.

## Note (not part of this brief, ask Ron)

Windows `panadapter.c` still has the old smoothing: sums `G_Smoothing` history frames plus
the current one in the `uint16_t` output buffer and divides by `G_Smoothing` (one frame too
many, overflows at 4). The Pi and Ubuntu fixed this 2026-09-25 (32-bit sum, clamp 1..4).
