# Build brief - cmd-048: QRP/QRO power cal owned by SDRcore-trans (port from the Pi)

**For:** Stew (N8VET)
**Host:** ubuntu-stew (the `linux/` tree) first, then windows-new-hp (Windows)
**Commit on each host when done. Do not push** (Stew pushes).
**Out of scope:** `rpi/` (done, the reference), WPF / Avalonia (no client change), firmware.
**No protocol change.** Same opcodes, same file formats (`power_cal.ini`, `amplifier_cal.ini`).

**Reference (Pi, installed in mscc 1.0.50 and tested on air by Ron 2026-09-28):**
commits `5e06637` (QRP) and `1b03de5` (QRO / amplifier). Whole change:
`git diff 5e06637^ 1b03de5 -- rpi/SDRcore-trans-linux rpi/ms-sdr-linux`

---

## Why

- Old way: every slider step on the Pwr Cal tab (0xA2 QRP, 0x08 QRO) made ms-sdr rewrite
  the ini file, send `CMD_SET_SDRCORE_TRANS_INITIALIZE`, and trans did a full `Init_Power_All`
  (about 70 log lines + 7 file ops per step, plus a 100 ms sleep). The slider lagged.
- Two files owned by two programs for one value (ms-sdr wrote, trans read).
- Trans 0xA2 wrote only one mode slot, chosen from the current main mode.
- `amplifier.ini` "user power" was never used (the client always sends 0xFA = 100).
- ms-sdr `Delete_amplifier_ini_file` had a `remove(homedir)` bug.

Result on the Pi: QRP and QRO cal sliders are smooth, power response very good (Ron).

## What changed (Pi)

**SDRcore-trans**
- `power.c`: trans owns `~/power_cal.ini`. `Create_power_cal_file` at startup (factory table
  47,30,24,29,53,72,28,30,45,40,40,40 = old ms-sdr PCB 2/4/5/6). `Init_Proficio_calibration`
  bounds/NULL-safe (defaults, then RECORD=n overrides). `Update_power_cal_file` writes tmp + rename.
- `udp_thread.c`:
  - 0xA1: unknown band -> index -1, so 0xA2 is ignored.
  - 0xA2: `Set_QRP_calibration()` sets all modes for the band, RAM only, and sets `G_drive_recalc`.
  - 0x08 (`CMD_SET_POTENTIA_CALIBRATION`, -99..0): RAM stack + table (`1 + v/100`) +
    `G_drive_recalc`, band bounds-checked.
  - 0xFA (`CMD_SET_AMPLIFIER_POWER`): no-op.
  - `Flush_pending_cal_saves()` runs before INITIALIZE's `Init_Power_All`.
  - `Get_Power_Mode_Index` removed.
- `driver.c` `Drive_Manager`: recomputes the drive on `G_drive_recalc`. It saves
  `power_cal.ini` / `amplifier_cal.ini` after about 500 idle loops (~0.5 s,
  `G_power_cal_save_countdown`, `G_amp_cal_save_countdown`), or right away before any
  `G_power_file_needs_updated` reload.
- `amplifier.c`: `Update_amplifier_calibration` writes RECORD/BAND = index (a missing file
  used to make every line RECORD=0), tmp + rename, 1 log line. `Init_amplifier_user_values`
  and `amplifier_table.user_power_value` removed.
- `main.c` / `extern.h`: new globals and prototypes.

**ms-sdr**
- `power_calibration.c`: read-only file load on 0xA1 -> GUI 0xB4. 0xA2 keeps a copy and is
  forwarded to trans (no file write, no INITIALIZE, no sleep). 0xB4 comes from the copy.
  Defaults (0xAA) ignored (the client never sends it). Create/Update/Delete + defaults tables removed.
- `amplifier.c`: no longer creates/reads/writes `amplifier.ini` (Check_Amplifier_Version,
  Create/Update/Delete/Initialize removed, including the `remove(homedir)` bug). 0xF9 replies
  0xFB = 100 (constant) + 0x08 cal from `amplifier_cal.ini` (read-only, bounds-checked).
  0xFA ignored.
- `main.c`: no longer creates `power_cal.ini` / `amplifier.ini` at startup.
- An old `~/amplifier.ini` left on disk is harmless.

## 2. Windows (`mscc-ui/windows-work-tree/`)

- `SDRcore-trans/sources/driver.c`, `amplifier.c`, and ms-sdr `amplifier.c` were identical
  to the old Pi versions, so they can be copied as-is.
- All other files differ, so port them hunk by hunk:
  - trans `udp_thread.c`, `main.c`, `extern.h`
  - ms-sdr `main.c`, `extern.h`
- `power.c` (trans) and `power_calibration.c` (ms-sdr) differ from the old Pi versions only
  by the Windows factory-seed calls. Port the Pi changes and keep those calls where they
  still make sense.

**Ask Ron before choosing: Windows factory seeding.** Windows ms-sdr has `factory_seed.c`:
- `Update_power_ini_file` calls `Factory_mirror_live_to_cal("power_cal.ini")`.
- QRP Reset (`CMD_SET_BAND_VOLUME_DEFAULTS`) calls `Factory_reseed_live_file("power", ...)`.
- The Pi has neither.

After the port, trans writes `power_cal.ini`, so the ms-sdr mirror no longer runs on save.
The options:
- (a) ms-sdr mirrors on the next 0xA1 (band select) / tab exit.
- (b) trans does the mirror.
- (c) drop it.
- QRP Reset: the Pi ignores 0xAA because the client never sends it. If Windows WPF does
  send it, keep the reseed and then send trans INITIALIZE, so trans reloads the file
  (`Flush_pending_cal_saves` runs first).

**Build:** Windows `GetTickCount`/`Sleep` are fine; nothing in this change is Linux-only
except `rename()`. On Windows, `rename()` fails if the target exists. Use
`MoveFileExA(tmp, dst, MOVEFILE_REPLACE_EXISTING)` or `remove()` + `rename()`.
Copy the builds to `C:\mscc-net9\` and report the versions.

## 3. Test (each host)

1. **Pwr Cal tab, QRP, 2 bands:** CALIBRATE, then drag the slider. The power follows
   smoothly with no lag. The trans log shows 1 line per step.
2. About 0.5 s after the slider stops, `power_cal.ini` shows the new value for that band.
3. Accept YES, then restart the servers. The value is kept, and the main operate power is
   right on that band in SSB, CW and TUNE (one cal value per band, all modes).
4. CANCEL: the old value comes back (the client sends 0xA2 with the previous value).
5. **QRO (amplifier) cal:** same checks with 0x08 and `amplifier_cal.ini`. Each line has
   RECORD=n, BAND=n (not all RECORD=0).
6. Delete `amplifier.ini` and restart: no errors. The amp power shows 100, and QRO cal
   still loads.
7. Delete `power_cal.ini` and restart trans: it's recreated with the factory table.
